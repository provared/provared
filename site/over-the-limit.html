Provared

An agent goes over its limit, and the record shows where

A worked example, for developers, 10 October 2026. Evidence, not a verdict.

Suppose an office agent is allowed to order stationery. The person it acts for wants three things: a limit on what it spends, a say on anything expensive, and a record that still stands up if the agent, the supplier or the person later disagree about what happened.

Logs do not give the third. A log is a file, and whoever runs the agent can edit it. Provared is a free, open format for signed records that a stranger can check later, with a free checker that reads them. This is what it shows on a small invented example: the sample record that ships with the library.

The permission

The person, "Sam Example", signs a permission with a passkey. Provared calls it a slip. It says:

  • the agent may place orders and send messages;
  • no more than 200 GBP of orders in total; no single order above 100 GBP; no more than 2 messages in any hour;
  • every order needs the supplier's countersignature, and an order above 60 GBP needs the person's own approval;
  • never destroy data, never claim to be a human being, never go around an access control, a block or a refusal;
  • from 5 October 2026 until 12 October 2026, to keep the office stocked.

The passkey signature binds the person to exactly these words: the slip's bytes are written in one canonical form, and their fingerprint is what the passkey signed. The slip also names the agent's two public keys (one of today's kind, one quantum-safe) and the supplier's, so that a checker needs nothing else to tell who signed what.

The receipts

For each action the agent signs a receipt, a stub, that points back to the slip and to the receipt before it. The supplier countersigns it where it takes part. The record is a text file with one entry to a line. Here is what the agent did on 5 October, in seven steps:

  1. Orders printer paper, 45 GBP. The supplier countersigns.
  2. Tells the office that the paper is ordered.
  3. Orders a toner cartridge, 80 GBP, after asking the person, who approves with the passkey. The supplier countersigns.
  4. Orders envelopes, 25 GBP. The supplier never confirms.
  5. Orders a second toner cartridge, 80 GBP, without asking. The supplier countersigns.
  6. Asks for 500 GBP of goods. The supplier refuses, and signs the refusal.
  7. Deletes the old order files.

Then whoever keeps the record seals it: one fingerprint over everything so far, signed with three keys, and time-stamped by an outside service.

And its summary:

Summary
  Is the record intact?                 yes
  Was every signature checked?          yes
  Did the agent stay within its slip?   NO: first at entry 5
  Time-stamped in a way you trust?      yes: the first 9 entries existed by 2026-10-05T10:16:00Z
  Checked against keys you named?       yes: the passkey you trust, and the recorder you expect

Two questions are kept apart on purpose. "Is the record intact" asks whether every signature checks and the chain is unbroken. "Did the agent stay within its slip" asks what the record shows. Going over a limit is not a fault in the record. It is what a sound record shows.

Step 6 is in the record too, as the supplier's signed refusal: "The action would pass a limit of the slip." It is shown as the supplier's statement and is not counted against the agent, because the agent placed no such order. Step 4 is one-sided: the agent says it ordered envelopes, and nobody confirms it. The checker does not guess which side is right. It says that the slip asked for a countersignature and there is none.

Before the action, not only after

The same rules run before an action. The library's stub writer asks "would this action be within the slip?" and takes the action only if the answer is yes. In the example, the second toner cartridge would have been stopped at step 5: with it the total passes 200 GBP, and the person had not approved it. The sample was written with that check switched off, so that the record shows what going outside looks like. The check before acting is a help to the agent's software. The record afterwards is the evidence.

The code that made the record

The sample is written by one tool in the repository, from the scenario the demonstration uses. The permission is these fields, handed to prepareSlip and signed by the person's passkey (in the sample, a software stand-in for one). The action names beginning provared. come from the format's shared list, so another organisation's checker knows what they mean; destroys is a kind of action, and impersonate and bypass are rules of conduct.

const fields = {
  issuer: { name: 'Sam Example (invented)', key: passkey.key, rpId: passkey.rpId, origin: passkey.origin },
  agent: { name: 'Office agent', keys: agent.keys },
  actions: ['provared.order.place', 'provared.message.send'],
  limits: [
    { action: 'provared.order.place', max: 200, unit: 'GBP' },
    { action: 'provared.order.place', each: 100, unit: 'GBP' },
    { action: 'provared.message.send', count: 2, per: 3600 },
  ],
  requires: [
    { action: 'provared.order.place', need: 'countersignature' },
    { action: 'provared.order.place', need: 'approval', above: 60, unit: 'GBP' },
  ],
  never: ['destroys', 'impersonate', 'bypass'],
  with: [{ id: 'supplier', name: 'Example Stationery (invented)', keys: supplier.keys }],
  validFrom: '2026-10-05T08:00:00Z',
  validUntil: '2026-10-12T08:00:00Z',
  purpose: 'Keep the office stocked with paper, pens and toner, and tell the office what was ordered.',
};

const prepared = await prepareSlip(fields);
const slip = assembleSlip(prepared, await passkey.sign(prepared.challenge));   // in a browser: signSlipWithPasskey

An agent's own software then opens the stub writer on a book that holds the slip, and asks it before each action. The writer asks the check before acting, takes the action only if the answer is yes, and writes the receipt, with the supplier's countersignature where the supplier gives one:

const recorder = await openRecorder({ book, slip: slipFingerprint, privateKeys: agent.privateKeys, issuerKeys: [passkeyThumbprint] });

const outcome = await recorder.act(
  { action: 'provared.order.place', amount: { unit: 'GBP', value: 45 }, with: 'supplier' },
  async () => placeTheOrder(),                       // taken only if the answer is yes
  { countersign: askTheSupplierToCountersign },
);
outcome.done;        // true: the order was placed and its receipt is in the book
recorder.book();     // the book, one entry to a line

The sample's receipts were written with that check switched off, so that the record shows what going outside looks like; the writer would have refused the fifth order. The seal is one more entry, signed with the recorder's three keys and time-stamped by an outside service.

What it does not show

The checker says this itself, at the end of every answer. It shows what was recorded, not what was left out: an agent that acts and writes no stub leaves no trace. A one-sided stub shows what the agent's side said. A refusal shows what the service's side said. It does not show that an action was wise, lawful or wanted. A rule of conduct, such as "never claim to be a human being", is the person's signed instruction, and no check can show that the agent kept it. It does not show who was holding the device when the passkey signed. A name in a record is a label; only keys are checked. What a record does not prove is stated beside what it does.

Try it

The sample record, with the checker naming the stand-in passkey, the recorder and the time-stamp service the sample was made with as trusted (a checker trusts nothing it is not told to trust):

npm install provared
npx provared-check --sample

A first record of your own, in three commands. The permission is signed with a development stand-in for a passkey; every permission it signs says so in its issuer's name, and the checker prints that name. The file first-record.mjs is in the repository and on the home page: it opens the stub writer under a permission that allows two messages, asks for three, and writes the book.

npm install provared
node first-record.mjs
npx provared-check book.jsonl --issuer <the thumbprint it prints>

The Python version (pip install provared) gives the same answers, with provared.dev for the stand-in, and provared-langchain puts every tool call of a LangChain agent behind the stub writer. The checking page checks a record in a browser, loading nothing from anywhere.

How it is built

From published standards only: JSON Web Signature (RFC 7515) for the envelope; one canonical form of JSON (RFC 8785); Ed25519 (RFC 8032) and ML-DSA-87 (FIPS 204) side by side on every receipt, with SLH-DSA (FIPS 205) as a third signature on a seal; W3C Web Authentication for the passkey; RFC 3161 time-stamps; the tree of RFC 9162 for proofs that one entry is in a book. The format is described exactly in one document, and its core is an individual Internet-Draft at the Internet Engineering Task Force. An Internet-Draft is a working document, not a standard.

How it compares, as the author read the others on 10 October 2026. Signed, chained and time-stamped receipts for an agent's actions exist elsewhere: at the Internet Engineering Task Force, the proposed AUDIT group has a draft of verifiable agent conversations (signed records with transparency receipts), and there are individual drafts for agent audit trails and agent receipts; the EMILIA Protocol's authorization receipts have a named person sign one exact high-risk action before it runs; an OAuth agent-delegation draft lets each step of delegation only narrow what was granted, and keeps no receipts; the payment networks' agent protocols (Google's AP2, Visa's Trusted Agent Protocol, Mastercard's Agent Pay) put spending caps on payments only, with the network holding the record; tracing tools such as Langfuse record tool calls, and neither sign them nor compare them with anything. What the author has found nowhere else is the permission the person signed with limits a machine can check, the checker's answer "did the agent stay within it", passing a permission on so that it can only narrow, and cancelling with the agent's signed acknowledgement. If you know a project that does one of these, say so: the list on the home page is kept honest.

Why I built it. I built Provared because after every story of an agent going wrong, the first question is what it was allowed to do, and the answer is usually a log that the same software wrote. I wanted that answer to be a signed permission and signed receipts that a stranger can check on their own device, without taking anyone's word for it.
