# Guard choices of step 3.7e: the Docker Compose recipe for claude.ai

One line each: the choice; why; the other way.

- **X313.** The recipe is one folder, `mcp-executor/recipes/claude-ai/compose/`, that the business copies whole. Why: one place to copy, update and back up beside. Other: the files beside the recipe's README.
- **X314.** The guard joins Caddy's network (`network_mode: service:caddy`) and listens on 127.0.0.1:8796, as its settings say. Why: the guard's rule (X109, X216) is kept, its port is published nowhere, and a `docker compose run` of a command shares the network too, so the guard's lock (an abstract socket, which belongs to a network) refuses a command beside a running guard. Other: the guard on an address of its own in an internal network (the guard warns, and its rule is loosened); or Caddy in the guard's network (a guard restart, more likely than Caddy's, would cut Caddy off).
- **X315.** While the guard runs, the start looks for Caddy's port (127.0.0.1:443) every 15 seconds; after 4 misses in a row it stops the guard (calls settled and receipted) and ends with code 1, so that Docker starts it again in Caddy's network. Why: the Docker check found that Caddy restarted on its own leaves the guard in the old network, answered 502, and `docker compose up -d` did not mend it. Other: a README line telling the business to restart the guard by hand.
- **X316.** The guard runs as user 10001, Caddy as 10002. Why: two users, so neither can read the other's keys; high numbers, unlikely to be a person's account on the server. Other: the Node.js image's `node` user (1000, often the first person's account on a server).
- **X317.** A third service, `folders`, runs once at each start as root with only `CHOWN` and `FOWNER`, no network, and gives each data folder to its user with mode 700 (the folder only, not what is in it). Why: Docker makes a missing bind folder as root's, which the unprivileged users could not write; it keeps the setup to one command. Other: a README step, `sudo install -d -o 10001 -g 10001 -m 700 guard-data` and the same for Caddy's, before `up`.
- **X318.** Caddy listens on 80 and 443 with no capability, by the network's own setting `net.ipv4.ip_unprivileged_port_start=80`. Why: with a non-root user and `no-new-privileges`, neither the file capability on Caddy's program nor `cap_add` reaches the process. Other: Caddy as root (the image's default) with `NET_BIND_SERVICE` alone.
- **X319.** Caddy's administration endpoint is off (`admin off`). Why: in the shared network the guard and the programs it starts could reach `localhost:2019` and change Caddy's routes. Other: the endpoint on a Unix socket in a folder only Caddy reads.
- **X320.** HTTP/3 off (`protocols h1 h2`); only 80 and 443 over TCP are published. Why: the founder's two ports; Caddy would otherwise offer HTTP/3 on a UDP port that is not open. Other: publish 443/udp and keep HTTP/3.
- **X321.** No email for the certificate authority, no access log, Caddy's default issuers. Why: as on the live server; the guard keeps its own log. Other: an email in `.env`.
- **X322.** The domain is `PROVARED_DOMAIN` in `.env`, Compose's own file, required (`${PROVARED_DOMAIN:?…}`), so that `up` stops and says what to set. Why: one file, read by Compose with no option. Other: an `env_file` named in the compose file.
- **X323.** The start takes a DNS name of two labels or more, lower-cased, with no scheme, port, path, final dot or IP address. Why: a browser makes no passkey for an IP address, and Caddy needs a name for its certificate. Other: leave it to Caddy and the guard to fail.
- **X324.** The start fills `oauth.issuer` and `oauth.clients` only where written `<like this>`. A settings issuer other than the domain stops the start, with the way to move; it is never rewritten. Why: the owner's passkey belongs to the issuer (DESIGN.md, 14.1); a silent change would strand it. Other: rewrite the issuer and reset the owner, which would end every connection unasked.
- **X325.** The recipe never signs the permission nor writes the thumbprint. The start waits, looking every 10 seconds, prints the steps once for each change, and runs `check` again once the settings or the permission change. Why: `issuerKeys` is what the guard trusts; taken from the permission it would trust whoever signed it. Other: end and let Docker restart it, which fills the log.
- **X326.** The owner's link goes to `guard-data/owner-link.txt`, mode 600, and never to the log; a later start keeps one with more than 2 minutes left, and the file is taken away once there is an owner. Why: Docker keeps logs in files on the server, after the link is used, and a log is easily shared. Other: print it in the log.
- **X327.** `owner` runs only in the start, before `http`, or as `docker compose run --rm guard owner [--reset]` with the guard stopped; its output names the file, not the link. Why: it changes the state file the running guard holds. Other: `docker compose exec`, which would run beside the guard (and be refused by its lock).
- **X328.** `docker compose run --rm guard <command>` runs any other guard command with `--config executor-http.json` put in (not for `secret`, `--help` or `--version`, or where `--config` is given). Why: the settings' name is fixed by the recipe. Other: the business types the whole command.
- **X329.** What the permission must hold goes to `permission-entries.json` (`keys --out`), not the log. Why: the public keys are long, and a file can be copied whole. Other: print it.
- **X330.** The start sets umask 0077, and mode 600 on the three files `init --http --demo` writes. Why: the Docker check found `content-rules.json` copied with the package's mode, 644. Other: leave the rules readable (they are no secret).
- **X331.** Node.js 24.22.3 on Debian 12 slim and Caddy 2.11.9 on Alpine, each by the digest of its multi-platform index, read on 17 November 2026. Why: the newest of each; the demo's 24.22.2 is older. Other: the demo's 24.22.2 digest of 1 November.
- **X332.** The guard's image has no name in the compose file: Compose names it `<project>-guard`; `folders` builds the same Dockerfile, from the builder's cache. Why: no name that looks published. (Corrected after review: compose.yaml fixes the project name, so it does not keep two copies of the folder on one server apart; they are one project, as the README's "One copy only" now says.) Other: one `image:` name with `pull_policy: never`.
- **X333.** Limits for a server with 2 GB: the guard 768 MB, one processor, 256 processes (up to 8 programs, `sessions.max`); Caddy 256 MB, half a processor, 128; logs 3 files of 10 MB; 30 seconds to stop; `init: true`; `/tmp` 16 MB, no programs. Why: room for the guard's programs, and a full disk or a stuck stop kept out. Other: no limits.
- **X334.** The update command is `docker compose build --pull && docker compose up -d`; the weekly timer (systemd, Monday 04:00 plus up to an hour, a missed week run at the next start) runs it, off until switched on. Why: the founder's one command and optional timer. Other: none here; see question Q1.
- **X335.** The recipe is not added to the package's `files`. Why: the package is what the image installs; the recipe builds the image and is taken from the repository, so in the package it would be a second, unused copy in every install, the image's included. Other: add `recipes/` to `files`.
- **X336.** The Docker check runs in the official `docker:29.7.2-cli` image with the Docker socket, its work folder at the same path for it and for Docker, and curl from `curlimages/curl:8.23.0` (curl's own image), both pinned by digest; host ports 127.0.0.1:18080 and 18443 in its override; `tls internal` put into a copy of the shipped Caddyfile. Why: modes and owners on a Windows folder are not Linux's; no curl in the CLI image; the ports of this computer kept free. Other: Docker in Docker.
- **X337.** The check and the test sign the permission with the library's development stand-in for a passkey, as the demonstration does. Why: no person can be asked in a test. Other: none.
- **X338.** A `.gitignore` in the recipe's folder leaves out `.env`, the three data folders, `pack/` and `compose.override.yaml`. Why: a business that keeps the recipe in a clone of the repository must not commit its keys. Other: none.

## After the founder's answers (Q1 to Q3)

- **X339.** Node.js follows `node:24-bookworm-slim` and Caddy `caddy:2.11-alpine`, with no digest (the founder's choice, Q1). The Dockerfile, the compose file and the README say which line, why, the versions tried (24.22.3, 2.11.9) and how to go back, each giving the digest of the version tried. This replaces the digest pins of X331. Other: the digest pins.
- **X340.** The update command is now `docker compose pull caddy && docker compose build --pull && docker compose up -d`, and the timer runs the same three steps. Why: `up -d` does not fetch a newer image for a tag it already holds, so without `pull` Caddy would never move. Other: `up -d --pull always`, which would also try to fetch the guard's image, which is only built locally.
- **X341.** `compose/package-lock.json` (lockfile version 3, SHA-512 hashes), installed with `npm ci --omit=dev --ignore-scripts` (Q3). The library's entry was written by npm from the registry. The executor's entry has the hash of a pack of a Windows working folder mounted into Linux (npm 11.19.1), where every file shows as executable, at the registry's address: a placeholder known not to match, since a pack of a clean Linux checkout gives another hash (corrected after review 3.7e; `package-lock.provisional.json` marks it, and `tools/release/check-recipe-lock.mjs` stops a release on it, X352). Why: 0.5.0 is not on npm, so its real hash does not exist yet. It is to be made again from npm once 0.5.0 is published, and checked against the hash the release run shows. Until then a hash that differs makes `npm ci` stop. Other: no executor entry, which `npm ci` refuses outright.
- **X342.** With a packed copy (`EXECUTOR` given), the build runs `npm install` in place of `npm ci`. It writes the executor's entry afresh, for the packed file, and keeps the library's entry and its hash. Why: the shipped lockfile names the registry's executor, and `npm ci` refuses a dependency that differs from the lockfile. Other: a second lockfile for the packed copy.
- **X343.** The README takes the recipe from a signed release tag: `git clone --depth 1 --branch <tag>`, then `git -c gpg.ssh.allowedSignersFile=.github/release-signers tag -v <tag>`, whose output must name the key in that file (Q2). The guard has no tags of its own. The repository's tags are `v` and the library's version (v0.1.0 to v0.8.0, made by the release workflow on `v*`), so the README says to take the newest such tag whose recipe names the guard's version. Why: these are the only release tags there are. Other: a tag form of the guard's own, which the release workflow does not make.

## Questions for the founder (answered: Q1 by X339, Q2 by X343, Q3 by X341)

- **Q1. Pins and updates.** Every version is pinned (npm exact, both images by digest), so the update command and the weekly timer bring nothing new until the recipe's files change. Should the guard follow a range (such as `~0.5.0`) and Caddy a moving tag, so that the timer brings fixes, at the cost of building what was not reviewed? Not decided here.
- **Q2. Where the business gets the recipe.** The README says to copy `compose/`; it does not say from where (the repository at a release tag?) or how the copy is checked. Not decided here.
- **Q3. No lockfile.** The image runs `npm install` with no `package-lock.json`: the tree is exact today (`provared` 0.7.0 has no dependencies), but npm's integrity hashes are not pinned. Should the recipe ship a lockfile with them? Not decided here.
